# Simon Part 6 — Video recording / playback app


Part of **Simon** → hub: https://github.com/Simon-Live/Simon-submission/tree/main/hub (scope lives there; this folder is only this part).
This repo is **only** Simon Part 6. It is a black box: it reads its input files and writes its output files, and knows nothing about the other parts. Keep it that way — that isolation is what lets agents work here with a small context.

Simon in one line (all you need): a trainer records an expected movement once; a follower performs it to camera; the follower's 3D movement is compared against the expected one and the differences are reported in plain words. This part is one step of that.

Source task: moalborati/simon issue #60. Scope source: `docs/MINI-APPS.md` in moalborati/simon (Part 6).

## Input

The phone camera (record) and the catalog (playback). Catalog entries are built from the shared files below.

## Output

A catalog of expected movements: each entry is a recorded video plus the `keyframes.json`, `skeleton.json` and `animation.json` produced from it, with a name a trainer can find again.

Recording's capture and processing are mocked. Record runs the whole flow (a mock camera view with a timer, Stop, name and type, Processing), and `part6/processor.py` then writes synthetic but valid `keyframes.json`, `skeleton.json` and `animation.json` for the new entry. That file holds the one function, `process(recording, report=None)`, the default processor. The real video to frames to 3D to animation chain replaces it with one setting, `--processor <module>:<function>` or `SIMON6_PROCESSOR`, and reports its stages (`queued`, `processing:<stage>`, `failed:<stage>: <reason>`, `done`), which the app shows while it waits. No other module produces shared files. Mock entries carry `"files_source": "mock"` and a "Mock recording" label in the app.

The catalog entry format is published as contract version 1: [CONTRACT.md](CONTRACT.md) and the JSON Schemas in [contracts/](contracts/). Part 7 reads entries through it and takes over at the Follow button.

### Catalog folder

One folder per entry under the catalog root; the folder name is the entry `id` (`^[a-z0-9][a-z0-9-]{0,62}$`).

```
<catalog>/<id>/manifest.json
<catalog>/<id>/keyframes.json   optional
<catalog>/<id>/skeleton.json    one of skeleton and animation is present
<catalog>/<id>/animation.json
<catalog>/<id>/thumbnail.svg
<catalog>/<id>/video.webm       or video.mp4, optional; the shipped fixtures have none
```

`manifest.json`:

```json
{"id": "squat", "name": "Squat", "video_uri": null,
 "keyframes": "keyframes.json", "skeleton": "skeleton.json", "animation": "animation.json",
 "created_at": "2026-10-27T00:00:00Z",
 "schema_version": 1, "category": "exercise", "description": "Bodyweight squat, three repetitions.",
 "thumbnail": "thumbnail.svg", "duration_ms": 10000, "files_source": "fixture"}
```

| Field | Meaning |
|---|---|
| `id`, `name`, `video_uri`, `keyframes`, `skeleton`, `animation`, `created_at` | the catalog entry above; file fields name files in the entry folder, or are `null` when the entry has no such file; `video_uri` is `null` when there is no video |
| `category` | `exercise` or `dance` |
| `description`, `duration_ms`, `thumbnail` | detail text, length in ms, preview drawing |
| `files_source` | `fixture` (shipped movements), `mock` (made by the mock Record flow), `import` (files another part produced, added with `part6 import` or the Import screen), `processor` (made by a plugged-in processor) |
| `provenance` | optional, per file: the producing part, its format id, how the format was found (`version` or `shape`), SHA-256 and size |
| `visitor` | optional, `true` on entries made through the app (Record or Import); the visitor cap counts these |

`skeleton.json` follows Part 3's `simon.skeleton/1` contract. `animation.json` is `simon.animation/1` at 30 fps: frames in the skeleton's shape with `interpolated` on each frame. Joints are the canonical 17 (subject's left and right), origin at the hip midpoint, x subject's left, y up, z anterior, metres.

The shipped output fixture is `fixtures/output/catalog/`: eight movements, regenerated by `python3 fixtures/make_catalog.py`. Six are synthetic, three exercises (Squat, Forward lunge, Jumping jack) and three dances (Side step, Arm wave, Hip twist). Two are Part 4's shipped sets, "Squat (Part 4)" and "Step-touch (Part 4)", whose files are copied byte for byte from simon-part-4-animate-keyframes at 9f4c073 (`fixtures/part4/SOURCE.md` names each file and its hash). The catalog root is `--catalog DIR`, else `SIMON6_CATALOG_DIR`, else `~/.local/state/simon-part-6/catalog`; a missing or empty root is seeded with a copy of the fixture catalog.

### Files from other parts

Part 6 reads every shape its neighbours write today. Each file is matched by its version field first, then by its shape, and a file no reader accepts gets one plain error naming the file and the field.

| File | Format | Written by |
|---|---|---|
| `animation.json` | `simon.animation/1` | Part 6 (its own provisional shape) |
| `animation.json` | `simon.animation.v1` | Part 4 |
| `skeleton.json` | `simon.skeleton/1` | Part 3 |
| `skeleton.json` | `simon.skeleton.v1` (key poses only) | Part 4's input, Part 3's Part 4 view |
| `keyframes.json` | Part 1's per-person shape (no version field) | Part 1 |
| `keyframes.json` | `simon.keyframes.v1` | Part 4's fixtures |

When an entry has no animation, the player plays its skeleton, holding each pose until the next one. Key frames on another clock (Part 1's 60 fps video, for example) are placed on the scrub bar by time. The readers exist twice, `part6/formats.py` for the server and `web/formats.js` for the player, and one golden suite in `fixtures/conformance/formats/` checks both.

### HTTP API

| Method and path | Result |
|---|---|
| `GET api/health` | 200 `{"ok": true, "entries": <n>, "contract_version": 1}` |
| `GET api/entries?q=<text>&category=<exercise\|dance>&source=<files_source>` | 200 `{"entries": [manifest, ...]}` sorted by name; `q` keeps names containing every word; 400 for an unknown category or source |
| `GET api/entries/<id>` | 200 manifest, 404 |
| `GET api/entries/<id>/<file>` | the named file (`Range` for a video), 404 |
| `POST api/entries` `{name, category, duration_ms}` | 201 manifest of the new entry when processing finished within 3 s, else 202 `{id, status, job}`; 400 for a blank or over-long name, unknown category or `duration_ms` outside 1000 to 120000 |
| `GET api/jobs/<id>` | 200 `{id, status, entry}` while a recording is processed, 404 |
| `POST api/import` `{name, category, files}` | 201 manifest; 400 with the reason in plain words; 408 when the body takes over 60 s; 413 above 24 MiB; 503 while another import runs |
| `GET api/contract` | 200 the contract document: schemas, formats, API and the hand-off |

Paths are relative to the server root, which `SIMON6_BASE_PATH` (default `/`) can move.

## Run it

The app needs only Python 3.12 and its standard library. The unit tests and `make check-6` also need pytest (`python3 -m pip install pytest`).

```bash
python3 -m part6 serve                            # http://127.0.0.1:8726
python3 -m part6 serve --host 0.0.0.0             # reachable from a phone on the same network
python3 -m part6 validate fixtures/output/catalog # exit 0 when every entry is valid
python3 -m part6 reset                            # drop recorded and imported entries, restore the eight movements
python3 -m pytest tests/part6 -q                  # unit tests
```

### Import, inspect and plug in

```bash
python3 -m part6 import path/to/folder --name "Squat" --category exercise   # keyframes.json, skeleton.json, animation.json, video.webm
python3 -m part6 import skeleton.json --name "Step" --category dance          # any mix of files
python3 -m part6 doctor ~/.local/state/simon-part-6/catalog/squat           # says what would fail, exit 0 when it plays
python3 -m part6 contract                                                   # the contract document as JSON
python3 -m part6 serve --processor fixtures.processors.part4_fake:process  # a fake processor with stages
```

`import` checks every file through the readers and writes nothing when one fails. In the app, the Import button on the catalog does the same from a phone: pick the files, see each one's format and what is missing, name it and import. `--follow-url` (or `SIMON6_FOLLOW_URL`) sets where Follow goes, with `{id}` and `{manifest}` filled in.

### Under a path prefix, with a cap on visitor recordings

`SIMON6_BASE_PATH` serves the whole app under a prefix, so a gateway can route one path to it. The web app uses relative URLs only, and a request outside the prefix gets a 404.

```bash
SIMON6_BASE_PATH=/simon-part-6 python3 -m part6 serve --max-recordings 30
# app:    http://127.0.0.1:8726/simon-part-6/
# health: http://127.0.0.1:8726/simon-part-6/api/health
```

`--max-recordings N` sets how many visitor entries the catalog keeps (entries made through the app, by Record or Import). After each save the oldest ones are removed until at most N remain. The default is 30, and 0 turns the cap off. The sample movements and entries added with `part6 import` are never counted or removed.

## Staging and the walkthrough video

The part also runs as a staged app behind a firm gateway, where it is checked as a visitor on a phone-sized viewport. The tooling that starts, checks and stops that stack, and the script that records the video, belongs to the firm workspace and is not published with this repo, so what ships here is the result: [demo/staging-walkthrough.mp4](demo/staging-walkthrough.mp4).

The video is one uninterrupted screen recording at the Pixel 7 viewport size. It opens the catalog, taps Dances, searches, opens a movement, plays it at 1x and 0.5x, turns it by dragging and switches Front, Side and Top. Then it goes to Record, stops after a few seconds, names the movement, picks Dance, saves and plays the new entry. It opens Part 4's shipped squat with its Files panel, then imports Part 4's version 1 files on the Import screen and plays the result. Nothing is seeded: the entries are made through the app in the recording and removed afterwards. How it was made and how to repeat it is in [demo/README.md](demo/README.md).

The staged app is the same server as the local run, set up with the two options above: it is served under the `/simon-part-6/` path prefix and keeps at most 30 visitor recordings. Recordings survive a restart, and the eight sample movements are always there.

## Done-check

`make check-6` needs Python 3.12 with pytest, and Node 22 or newer. It installs the pinned `playwright` from `package-lock.json` when `node_modules` is missing, starts the server on a temporary catalog and drives the app in headless Chromium under Pixel 7 emulation: search, filter, detail, the 3D player (orbit, zoom, views, play, pause, scrub, 1x and 0.5x) and the mock Record flow. It prints one metrics JSON line and exits 0 only when every threshold passes. If Chromium is missing it says so; run `npx playwright install chromium` once.

`make check-6-contract` checks the conformance kit the same way: the golden suite in Python and in the browser module, `part6 doctor` on the eight entries in `fixtures/conformance/entries/` (two per `files_source`), the contract endpoint, each entry playing on the Pixel 7 viewport with its formats shown, the skeleton fallback, a format error, the Import screen, a fake processor's stages and failure, and the Follow event.

## Shared-file context (only what this part touches)

A catalog entry: `{id, name, video_uri, keyframes, skeleton, animation, created_at}` referencing the shared files by name. This repo owns recording/playback/catalog UI only — it does not compute key frames, pose, or faults.

## Definition of done

Record a movement and it appears in the catalog with its animation; play an entry back at full and half speed with play/pause/scrub, on a phone browser.

Done-check: `make check-6` — prints a metrics JSON and exits 0 only when every threshold passes. Write the check as part of this work; until it exists, the stub in the Makefile fails honestly.
