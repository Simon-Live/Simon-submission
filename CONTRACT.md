# Part 5 contract

What Part 5 reads and writes, which part sends what, and how to check a file before you stitch. Field rules are in `docs/schemas.md`; this page says who sends what and what each side must do.

## Check a file now

```bash
python -m part5 doctor skeleton.json                  # a clip Part 5 would read (expected or follower)
python -m part5 doctor analysis.json --for part7      # an analysis a viewer would read
python -m part5 doctor replay.json                    # the replay file (simon.replay.v1) a viewer would draw
python -m part5 doctor pose3d.json                    # a Part 2 pose3d.json as the optional feet side input (not a clip)
python -m part5 contract                              # the schemas, the word list (student-words.json), the history fields (history-fields.json) and the compatibility table below
python -m part5 contract --schema analysis            # one schema, exactly as stored
make check-5-contract                                 # schemas, fixtures and golden outputs agree
make test-contract                                    # every file below through part5.io.load_clip, and against its schema
make contracts-check                                  # exit 1 when a copy differs from Part 3 or Part 4 main
make contracts-sync                                   # refresh the copies and contracts/sources.lock.json
```

`doctor` names the file's kind and version, validates it and, when the consumer would reject it, says which field is wrong and which option fixes it:

```
$ python -m part5 doctor skeleton.native.json
skeleton.native.json: simon.skeleton/1 (Part 3 native); rejected for part5
  no "format" field: this is Part 3's native skeleton.json (simon.skeleton/1); fix: rerun Part 3 with --view part5
```

Exit codes of `doctor`: 0 accepted, 1 rejected, 2 unreadable (missing, not a file, not JSON). `--json` prints one object. `--for part7` checks an `analysis.json` (or a `replay.json`, which either option accepts) instead of a clip. `contract` and `doctor` run offline, and Part 5 never fetches a URL, a hand-off's included.

## Schemas

Each schema is JSON Schema draft 2020-12 with an `$id` and a top-level `version`. Any validator reads them; Python is not needed.

| Name | Version | File | Describes |
|---|---|---|---|
| `analysis` | `1.13.0` | `contracts/analysis.schema.json` | Part 5 analysis.json (simon.analysis.v1) |
| `input-animation` | `1.0.0` | `contracts/input-animation.schema.json` | Part 5 input clip (simon.animation.v1) |
| `input-skeleton` | `1.0.0` | `contracts/input-skeleton.schema.json` | Part 5 expected skeleton (simon.skeleton.v1) |
| `labels` | `1.0.0` | `contracts/labels.schema.json` | Part 5 labels.json (evaluation labels) |
| `metrics` | `1.5.0` | `contracts/metrics.schema.json` | Part 5 make check-5 document (simon.part5.check.v1) |
| `replay` | `1.0.0` | `contracts/replay.schema.json` | Part 5 replay.json (simon.replay.v1) |
| `input-feet` | `1.0.0` | `contracts/input-feet.schema.json` | Part 5 optional feet side file (a Part 2 pose3d.json with `extra_joints`, no `format`) |

`contracts/student-words.json` (`simon.student-words.v1`) is not a schema: it holds the word lists Part 7's guard shares with Part 5's validators (Part 7's duty 11 below).

`contracts/history-fields.json` (`simon.part5.history-fields.v1`, version `1.2.0`) is not a schema either: it is the allowlist of the `analysis.json` fields a report across a person's takes should read, with the meaning, units, direction, side convention and first schema version of each (History across takes, below).

The copies of Part 3's and Part 4's schemas stay under `contracts/part3/` and `contracts/part4/`, exactly as they were published. The analysis schema is `1.13.0`: it adds optional fields to `simon.analysis.v1`, so a `1.0` document still validates and `format` does not change. `1.3.0` adds `faults[].reps`, `diagnostics.guard.reps`, `diagnostics.expected_reference` and `score.per_rep`, written only for a take compared one repetition at a time (ADR-0010); `1.4.0` (ADR-0012) adds the top-level `warnings` and `match`, `score.capped_by` and a fault `confidence` of `"low"`, written only for a take that earned a warning; a document without warnings keeps its earlier `schema_version` (`1.2.0`, or `1.3.0` for a take compared by repetition). The replay (`simon.replay.v1`) of such a take adds an optional `reps` list. `1.5.0` (ADR-0014) adds coaching cues to every new document, which is therefore always `1.5.0`: `faults[].cue` and `cue_kind`, the same with `direction` on each `score.timeline[].misses[]`, `score.timeline[].tempo` and `score.tempo`, and the top-level `insights`. `1.6.0` (ADR-0015) adds the foot measures to every new document's vocabulary: faults with `measure` `foot_rotation` or `ankle_inversion` (`body_part` `feet`, `joint` an ankle) and `diagnostics.feet`, both written only when a Part 2 `pose3d.json` with foot points was given for a clip (below); a document without them is exactly what `1.5.0` was apart from `schema_version`, which is `1.6.0` on every new document. `1.7.0` (ADR-0016) adds the analysis profile to every new document, which is therefore always `1.7.0`: the top-level `profile` (`dance`, `rehab` or `fitness`, always written, `fitness` being the default and the analysis as it was); under the `dance` profile only, `score.components.tempo` (and the same on each window) says how many points the pace cost. A score is read within its profile. `1.8.0` (TICKET-043) adds `diagnostics.near_misses` to every new document whose take was compared (absent on a take that could not be aligned): `{total, omitted, items}`, the candidate faults detection considered and dropped (a measure, side and direction with a frame past its threshold that failed persistence or was explained by a kept fault), largest first, at most 10; each says the size, the frames over and where, what persistence needed and why it was dropped. It changes no fault, score or other field; it is for people debugging a take ("why no fault?") and is not shown to the follower. `1.9.0` (TICKET-045, TICKET-046, `docs/specs/second-opinion.md`) adds `phrasing.lang` (and `phrasing.lang_requested` when the tag asked for is not listed as given) and, per fault, `phrasing.faults[].text` (the line shown, equal to the fault's `coaching`) and `phrasing.faults[].lang` to every new document, and the top-level `second_opinion` when the two clips were given as videos: Muse Spark's view of the take (`status` `ok`, `fallback` or `skipped` with a `reason`; `verdicts` `{fault_index, agrees, note}`; at most 2 `observations` `{at_s, text, label: "model_opinion"}`), which the score, faults and insights never read. The same `1.9.0` adds `score.uncapped` (`{value, grade}`, Part 7 TICKET-155: the value and grade before a warning capped the score at 59 F, written only when the cap lowered them, so a reader can say what the warning cost) and, for TICKET-048, the optional top-level `source` (the producing part, `part5` or `part7`; absent means `part5`, and Part 5 never writes it) and the `no_person` code in `warnings[].code`: Part 7 writes its own `analysis.json` (`source` `part7`, `schema_version` `1.4.0`, `faults` `[]`, `expected` and `follower` with their real `path`, a score of 0 grade F, no `match` because nothing was compared) when Part 2 finds nobody in a take; Part 5 never writes `no_person`, and `part5 doctor <file> --for part7` accepts such a document. `1.10.0` (TICKET-047, ADR-0018, `docs/specs/score-v2.md`) allows the score of a new document to be `simon.score.v2`: read `score.version`, which names the score a document was made with. `simon.score.v2` failed held-out score seed 59 (docs/thresholds.md), so ADR-0018's fallback shipped `simon.score.v1` inside the same `1.10.0`; `simon.score.v3` (below) then held all five targets on score seed 61 (docs/thresholds-score-v3.md) and ships, so the rules in this tree carry it, and `score.version` says which one a document was made with. Under v2 a miss costs less on a measure the trainer moves little in its window, never below a floor, and a take that reports a fault (`faults` not empty) scores at most 89, a B. The new `score.fault_cap` is that ceiling as an integer (89), written under v2 when the take reports a fault whether or not it lowered the value, and absent otherwise; it is not a warning, and `score.capped_by` keeps its meaning exactly (the warning codes of the low-match cap at 59 F, nothing else). `score.uncapped` (`{value, grade}`) is now the value and grade before every cap, the fault cap and the warning cap: it is written when either lowered the value (with both, the value before the first), so a faulted take with no warning that the fault cap lowered has `uncapped`, `fault_cap` and no `capped_by`. While the rules ship v2 or v3, `fixtures/output/analysis.fault-capped.example.json` is a sample (one fault, value 89 B, `fault_cap` 89, `uncapped` 94 A). A `1.9.0` document and every earlier one still validates. `1.11.0` (TICKET-060, ADR-0019, `docs/specs/score-v3.md`) allows the score of a new document to be `simon.score.v3`, the retry after v2 (v3 keeps v2's weight and its ceiling of 89 for a take that reports one fault, and adds a ceiling of 79, the top of C, for a take whose `faults` list holds two or more entries). `score.fault_cap` is now the ceiling in force: 89 for a take that reports one fault, 79 for two or more, written whether or not it lowered the value; read it, never assume 89. `score.uncapped` and `score.capped_by` mean exactly what they meant in `1.10.0`: `uncapped` is the value before every cap, `capped_by` the warning codes of the low-match cap at 59 F and never a ceiling. The rules in this tree ship `simon.score.v3`: it held all five targets on score seed 61 (docs/thresholds-score-v3.md, ADR-0019), so v3 is the shipped score and is not provisional. `make score-fallback` remains the reversal recipe: it puts `simon.score.v1` back inside the same `1.11.0` and no `fault_cap` is written. While the rules ship v3, both samples are written: `fixtures/output/analysis.fault-capped.example.json` (one fault, `fault_cap` 89, above) and `fixtures/output/analysis.double-capped.example.json`, a real take that reports two faults (value 79 C, `fault_cap` 79, `uncapped` 82 B, no `capped_by`); after `make score-fallback` neither is written. A `1.10.0` document and every earlier one still validates. `1.12.0` (TICKET-071, `docs/specs/history-per-rep.md`) adds three fields for comparing takes with each other; no fault, score or insight reads them. A fault of a take compared one repetition at a time has `rep_sizes`: one `{rep, magnitude_deg, side, body_part}` for each rep in its `reps`, the fault's size in that rep, signed like its `magnitude_deg`, and the side that rep found it on. Each `score.per_rep` entry has `rep` (the follower repetition, the index `reps` uses) and `tempo_ratio` (that rep's `tempo.ratio`, follower seconds per example second); `tempo_ratio` is null where the rep could not be timed and for every rep of a low match, which is not measured and never on time (TICKET-063). Each `diagnostics.near_misses` item has `margin_deg`, `abs(magnitude_deg)` minus `threshold_deg` to 0.1 degree: positive when the candidate went past the threshold by that many degrees before persistence dropped it, 0 on the threshold, negative short of it. Detection lists a candidate only when a frame is past its threshold, so `margin_deg` is 0 or more today. A `1.11.0` document and every earlier one still validates. `1.13.0` (ADR-0020) adds `score.credit` (`simon.credit.v1`), a DDR-style credit display beside the score, to every new document: `{version, percent, grade, points, max_points, tolerance, levels: {easy, normal, hard}, bands, points_per_measure_second, per_window}`. Each measure seen in at least half of a compared window's frames earns, on each frame it is measured, 1.0, 0.6 or 0.2 when the follower is within 0.5, 1 or 2 of that measure's detection thresholds of the example (the level's tolerance scales the thresholds: easy 1.5, normal 1.0, hard 0.7), else 0; `percent` is credit earned over credit possible, `points` count 100 per measure per second times the level's multiplier (0.75, 1.0, 1.5), and `per_window` has one entry per compared window of `score.timeline`, same `t_s`, same order. `score.credit` is null when nothing was compared. It is additive: `value`, `grade`, `components`, `fault_cap`, `uncapped` and `capped_by` are unchanged, nothing reads it back, and the 59 warning cap does not apply to it (so read `warnings` before showing it). A `1.12.0` document and every earlier one still validates. The earlier groups stay optional and are told apart by their fields. The `metrics` schema is `1.5.0`: `1.1.0` added the score report that `make check-5` writes (`gate.sweep`, `report.score`, `detection_sha256`) and `1.2.0` adds `report.refusals.gated` (always `false`, beside the slice keys, so every report block carries `gated: false`); `1.3.0` adds the optional top-level `profiles_sha256` (the hash of `part5/profiles.json`, printed for information; `make check-5` runs the `fitness` profile only); `1.4.0` (ADR-0018) lets `report.score.version` be `simon.score.v2`; `1.5.0` (ADR-0019) lets it be `simon.score.v3`; a `1.0.0`, `1.1.0`, `1.2.0`, `1.3.0` or `1.4.0` check document still validates. The `replay` schema is `1.0.0` and describes the second file `part5 analyse --replay` writes (below).

## What Part 5 writes

`part5 analyse --expected <file> --follower <file> --out <analysis.json> [--replay <replay.json>] [--live] [--expected-feet <pose3d.json>] [--follower-feet <pose3d.json>] [--expected-feet-person N] [--follower-feet-person N] [--profile {dance,rehab,fitness}] [--lang <bcp47>] [--expected-video <mp4> --follower-video <mp4>]` writes `analysis.json` (`simon.analysis.v1`, schema `1.10.0`; documents written before TICKET-047 are `1.9.0`, before TICKET-045 are `1.8.0`, before TICKET-043 are `1.7.0`, before ADR-0016 are `1.6.0`, before ADR-0015 are `1.5.0`, before ADR-0014 are `1.2.0`, `1.3.0` for a take compared one repetition at a time, or `1.4.0` when the take has a warning). A take is always analysed (ADR-0012): the exit code says what happened to the file:

| Exit | Meaning | `analysis.json` written |
|---|---|---|
| 0 | the analysis is written; `status.code` is always `ok`, and `warnings` (when present) say why the grade is capped at F | yes |
| 1 | an input or the output breaks the contract: an unreadable or malformed clip, a clip over the size bounds, an output that cannot be written | no |
| 2 | usage: a missing or unknown option | no |
| 3 | not used since ADR-0012 (it was a refused analysis) | no |

`analyse` never refuses a take. What was a refusal is a warning: `warnings: [{code, text}]` with `low_match` (the guard would have refused: `match.quality` is `low`), `moving_part_out_of_frame`, `not_enough_visible` or `no_usable_measures`. The analysis runs best effort on the measures the camera sees (with none, no faults and a score of 0), `score` is never null, and any warning caps `score.value` at 59 (grade F) and names the codes in `score.capped_by`. On a low match each fault carries `confidence: "low"` (a number in 0..1 otherwise). A correct, matching take has none of these fields and is unchanged.

### The replay file

`--replay <replay.json>` also writes `replay.json` (`simon.replay.v1`, schema `1.0.0`, `contracts/replay.schema.json`) after `analysis.json`: both normalised skeletons, matched frame for frame, for a 3D replay. Keys: `format`, `schema_version`, `fps`, `joints` (the 17 names), `bones` (index pairs to draw), `expected` and `follower` (per frame, 17 entries of `[x, y, z]` in metres to 4 decimals or `null`; hip midpoint at the origin, x the subject's left, y up, z forward), `expected_t` and `follower_t` (seconds as written in each input file, strictly increasing), `exp_to_fol` (the follower file's frame shown at each expected frame) and `coordinate_frame`. A take compared one repetition at a time adds `reps`. The timeline runs on the expected clip's frames: at expected frame `i` show follower frame `exp_to_fol[i]`. An unwritable replay path ends with exit 1 and `part5 analyse: cannot write <path> (<reason>)`; the analysis that was written stays. `python -m part5 doctor replay.json` checks the schema, that `expected`, `expected_t` and `exp_to_fol` have one entry per expected frame and `follower` and `follower_t` one per follower frame, that every `exp_to_fol` and bone index is in range and that both time lists strictly increase.

### Live mode

Live mode is on with `part5 analyse --live`, `part5 serve --live`, `SIMON5_LIVE=1` or `META_LIVE=1`. Muse Spark then writes each fault's `coaching` line (including its time) unless `--phrasing` names a backend, and `phrasing.selected_by` is `live`. It needs the Baseten key file on the host that runs Part 5; without it each fault keeps its timed template line with `fallback_reason: "no key"`. The line never changes `text`, `cue` or the score. Without live mode the phrasing is `template` (`selected_by` `default`), which is what the tests, `make check-5`, `make check-5-contract` and `make output-examples` always use, whatever the environment.

## Part 7's duties

1. **Read `warnings` and `score`.** From `1.4.0` `status.code` is always `ok`; show each `warnings[].text` beside the grade F. `status.text` of a take with no warning is "Compared with the expected movement."; of a take with one it is "Compared with the expected movement, with a warning that caps the grade at F.", and with more than one "Compared with the expected movement, with 2 warnings that cap the grade at F." (the number of warnings in place of 2). The code stays `ok` and the text does not replace `warnings[].text`, which say what each warning is. Only a document written before ADR-0012 can still carry a refusal: it has `status.code: "different_movement"` (or `"not_enough_visible"` or `"moving_part_out_of_frame"`: too little of the body, or the part the example moves, is in frame; show `status.text`, which says what to change; ADR-0011), a `status.text` that says why in plain words and `faults: []`. Show it as a refusal, never as "no faults". A file with no `status` block is a schema `1.0` file: read it as `ok`.
2. **Treat exit 0 as "written".** Part 7 at 90aa473 expects the family codes 0 written, 1 not writable, 2 input or option breaks the contract (Part 3 `CONTRACT.md`, row for Part 7). Map 0 to "written" and 1 and 2 to failures.
3. **Highlight `faults[].joints`.** It lists canonical joint names. A `1.0` file has no `joints`; then map the fault's `joint`: a sided joint is itself; side `both` is `left_X` and `right_X`; `spine` is both shoulders and both hips; `shoulders` is both shoulders; `neck` is the nose and both shoulders.
4. **Ignore fields you do not know.** New fields are added without changing `format`; `schema_version` says which additions to expect. `diagnostics` is for people debugging a take and is not shown to the follower.
5. **Show `coaching` when it is there, `text` when it is not.** `text` is a lowercase fragment ("left foot too far out"); capitalise it for display. From `1.2.0` the template phrasing makes `coaching` equal `text_timed` (the same words with the direction said as a side and plus the time, "left foot too far left at 1.9 s"; a thigh not lifted reads "right thigh not raised enough", an arm held low "left arm too low"), and `text` stays as it was.

6. **Show `insights` as what to work on.** From `1.5.0` each item is `{cue, why, kind, at_s, window, points}`: `cue` is an imperative of at most 6 words ("Bend your knees more"), `why` what was seen and where (when it points at a fault, that fault's own `text_timed` words in sentence case, "Right foot too far right at 1.9 s", so the row and the insight match; when the fault's `coaching` was written by a live model and passed the word test, `phrasing.faults[i]` having a backend other than `template`, no `fallback_reason` and `lang` `en`, the observation clause of that line, its text before the first ";", at the insight's own time: "Your right foot drifts too far to the right at 1.7 s"; a count such as " (3 of 8 reps)" or " (2 times)" follows when the cue missed more than once), `kind` `position`, `range` or `tempo`, `at_s` the follower time to seek to, `points` what it cost the score (null for tempo and for a take without a timeline). Show each fault's and each miss's `cue` beside its text, and a window's `tempo.cue` when it is not null. A document without `insights` was written before `1.5.0`: show it as before.

7. **Show the time, the direction, the score and the replay.** `at_s` (and `follower_t_s`) is the moment on the follower file's own clock to seek to; `follower_runs` maps every run to follower frames. `lateral` (`left`, `right` or `null`) is the subject's own left and right, like `side`: mirror it only when you draw a mirrored view. `lateral_m` (metres, `foot_out` on one side) is how much further out the ankle is than the example's. `score` is `{version, value, grade, components, params_sha256}` plus `basis`, `timeline`, `tempo`, `capped_by` and `credit` (1.13.0, ADR-0020) when present: show `value` out of 100 with `grade` A to F, the faults first, and each `timeline` window with its `misses`. A fault whose `confidence` is the string `"low"` came from a low match: show it as less certain. On a low match (`match.quality` `"low"`) every `tempo` in the document, the take's and each window's or rep's, is `{ratio: null, cue: null}` and every `score.per_rep[].tempo_ratio` (1.12.0) is null: the timing was not measured, so show it as not measured, never as on time (TICKET-063). The replay (`replay.json`) is optional; `exp_to_fol` says which follower frame goes with each expected frame.

8. **A foot fault needs a 1.6.0 reader, and then nothing else new.** From `1.6.0` a fault may name `foot_rotation` or `ankle_inversion` (`body_part` `feet`, `joint` `left_ankle`, `right_ankle` or `ankle` for side `both`). A document that holds such a fault is rejected by a reader built on the 1.5.0 or an earlier schema, because its `measure` and `body_part` enums do not list those values: update the reader to `contracts/analysis.schema.json` 1.6.0 first. A 1.6.0 document with no foot fault (every pair given no feet file, and every pair whose feet showed nothing) reads with an older schema too, apart from `schema_version`. With a 1.6.0 reader, `faults[].joints` is the ankle, so highlight it as for any fault, and show `cue` and `text_timed` as usual ("Turn your left foot out", "Keep your left ankle straight", "Stop your left ankle rolling in"). `diagnostics.feet` (debugging only) says whether the foot measures were compared and why not.

9. **Pass the mode, and read a score within its profile.** From `1.7.0` Part 7 may pass the operator's mode (dance, rehab or fitness) as `part5 analyse --profile <name>` or as the `profile` field of `POST api/analyse`; probe `part5 analyse --help` for `--profile` before relying on it, and send nothing for `fitness`. A name that is not one of the three is exit 2 on the command line and HTTP 400 on the API. Every document carries `profile`; a document without it (before `1.7.0`) is `fitness`. `dance` and `rehab` only loosen how picky detection is, so for the same take they never report a fault `fitness` does not (one `fitness` reports on both sides may be kept on one side; this holds for a take compared repetition by repetition too), but their grades are not comparable with `fitness`: a dance 84 and a fitness 84 mean different things, so never rank or average scores across profiles. `rehab` says "Slower is fine" where the other two say "Speed up to match the trainer"; `dance` charges the pace in the score (`score.components.tempo`). The tolerances are set by hand, not calibrated on any labelled dancer or patient (`docs/specs/profiles.md`).

10. **Read the fields of a takes-over-time report the same way in every version since `1.5.0`.** A report across many takes (Part 7 TICKET-183) reads `faults[].measure` and `side` (required in every version), `faults[].at_s`, `follower_t_s`, `text_timed` and `cue` (optional in the schema), `score.timeline[].misses[].cue` and, inside `score`, `score.value` (an integer 0 to 100) and `score.grade` (`A` to `F`). `score.value` compares only within one `score.version` (read it: `simon.score.v1` in every document up to `1.9.0`, `simon.score.v1` or `simon.score.v2` from `1.10.0`, and `simon.score.v3` as well from `1.11.0`; a v2 or v3 value is not on the v1 scale, nor a v3 value on the v2 scale, ADR-0018, ADR-0019), as it compares only within one `profile`; do not draw them on one axis. `score.fault_cap` is the ceiling in force, 89 or 79 under v3: read it, never assume 89. `at_s`, `follower_t_s` and `text_timed` date from `1.2.0`, both cues from `1.5.0`; `score` is optional in the schema and always written from `1.4.0`; `misses` exists on a compared window only. Part 5 writes every one of them on every fault, so an absent field means an older document, or Part 7's own (the no-person document has `faults: []` and no timeline): leave an untimed fault off the time axis, show `text` when `text_timed` is absent and no cue when `cue` is. `at_s` and `follower_t_s` are seconds on the follower file's own clock, `at_s` being `follower_t_s[0]` rounded half up to 0.1 s; `text_timed` is the timed words plus ` at <at_s> s`; a miss's `cue` is the cue of the fault it came from. There is no field for the follower's duration in `analysis.json`: read the end of the compared span from `score.timeline[-1].t_s[1]` (the duration when the whole clip was compared, less when the follower stood still at the end) or, from the optional `replay.json`, the exact duration `follower_t[-1]` (the last frame time of the follower file). `tests/test_contract_part7_history.py` pins all of this for `1.5.0` to `1.11.0` and fails when a schema version is added without being pinned.

11. **Refuse the same words Part 5 does.** `contracts/student-words.json` (`simon.student-words.v1`, version `1.0.0`; not a schema) holds the banned word stems and the praise phrases Part 5's validators use, so a guard that reads it refuses the same lines. `banned` entries end in a trailing `*`, meaning any word that starts with what precedes it (an entry without `*` would be a whole word); `praise` entries are phrases of whole words. `match` states how to apply both: case-insensitive on the lower-cased line, word-bounded, the words of a phrase joined by any whitespace or hyphen, zero-width characters (`ignored_characters`) ignored. `applies_to` says where Part 5 tests each list (the banned stems guard the second opinion's notes; praise guards every model-written fault line too), `sources` names the Part 5 constants and `lists_sha256` changes when a list does. The file is generated by `make student-words` from those constants, and `tests/test_student_words.py` fails when the committed file differs from what the script generates.

12. **Read `quality`: detect it by presence, and apply the cap yourself.** From `1.13.0` every new document carries `quality` (`simon.quality.v1`, `$defs.quality` in `contracts/analysis.schema.json`). It is optional in the schema, so test for the key and read a document without it as not assessed. `level` is `ok`, `degraded` or `major`; `reasons[]` says why, each `{code, words, value, threshold}` and sometimes a `joint`, with `code` from a closed list (`not_enough_visible`, `moving_part_out_of_frame`, `no_usable_measures`, `joints_unseen`, `joints_missing`, `frames_missing`, `measures_hidden`, `position_jitter`) and `words` one plain sentence to show as it is; `signals` holds the raw readings, `null` where a reading cannot be made and never 0 in its place. `score_cap` is 59 when `level` is `major` and `null` otherwise. **The cap is reported only.** `score.value`, `score.grade`, `score.fault_cap`, `score.uncapped`, `score.capped_by` and `warnings` are what they are with or without the block, and the block never adds a `warnings` entry, so a `major` take can carry a `score.value` above 59: if your gate caps it, apply `score_cap` yourself and say that you did. A take that carries the warning `not_enough_visible`, `moving_part_out_of_frame` or `no_usable_measures` is `major` with that reason; `low_match` is not a quality reason. `words` names no cause, because no part gives Part 5 a light reading: a dark take shows as joints that jump from frame to frame or go missing, and one that the estimator holds steady with every joint at confidence 1.0 can read `ok`. The limits are in `part5/quality.json`, a file of their own that `rules_sha256` and the score `params_sha256` do not read, and `make report-quality` reports how they sort the seed 5 and the held-out seed 73 takes.

`python -m part5 doctor analysis.json --for part7` checks all of this on a file, warns when `status.code` is not `ok` or the take has `warnings`, and notes the score (and what capped it), the timed faults, the faults at confidence `"low"` and the `profile` ("scores compare within one profile"; a document before `1.7.0` has none and is read as `fitness`) and, from `1.8.0`, how many near misses `diagnostics.near_misses` lists (for debugging, not for the follower); from `1.9.0` the language of the lines and the second opinion's status and counts. From `1.10.0` it notes the score version (and that `score.value` compares only within one `score.version`) and, when the document has them, the fault cap (`score.fault_cap`, under v2 or v3: the ceiling in force, with how many faults the take reports) and, when a cap lowered the value, the value before it (`score.uncapped`).

The same command notes `quality` when the document has it: its level, its reasons in `words` and, for `major`, the cap of 59 that is reported and not applied. A document without the block is noted as not assessed.

## History across takes

`contracts/history-fields.json` (`simon.part5.history-fields.v1`, version `1.2.0`; not a schema) is the allowlist of the `analysis.json` fields a report across a person's takes should read, written for analysis schema `1.13.0`. Each entry gives the path, what it means, its units, which way is worse, the side convention, the schema version it first appears in (`since`), whether it is `stable` or `additive`, when it is written and what changed across versions. An entry whose value is a letter grade carries `order`, its letters best first as the schema's enum lists them: `["A", "B", "C", "D", "F"]` for `score.grade`, `["S", "A", "B", "C", "D", "E", "F"]` for `score.credit.grade` and the letters of `score.credit.grades`; both use the direction `later_letter_is_worse`, so rank a letter by its place in `order`, never by the alphabet, where S would be the worst. The file also holds `absent_means` (what an absent fault, a null tempo, an absent measure and `diagnostics.near_misses` mean), `score_versions` (what v1, v2 and v3 change), `measures` (what `more` and `less` mean for each measure) and `detection_changes_without_a_version`. `python -m part5 contract` names it, and `part5 contract --json` lists it under `history_fields`. `tests/test_contract_history_fields.py` fails when a path leaves the schema, when a `since` disagrees with the committed examples, or when the schema moves to a version the file does not describe. Compare takes by `score.version` first and `profile` second.

**Units, and which way is worse.** Every fault is sized in degrees. `magnitude_deg` and `peak_deg` are the follower's value minus the example's, with a sign, and `threshold_deg` is the size the difference had to pass. Nothing is a ratio, and nothing is scaled to the body or the clip. `direction` `more` is a positive difference and `less` a negative one. Neither is better, and a bigger absolute size is worse. Two measures are not on one scale because each has its own threshold: divide by `threshold_deg` to compare them, within one profile. The only length is `lateral_m`, in metres. A tempo `ratio` is follower seconds per example second, and the further from 1.0, the bigger the pace difference. From `1.12.0` a take compared one repetition at a time also gives each fault's size in each repetition (`faults[].rep_sizes`: `rep`, `magnitude_deg`, `side` and `body_part`, in the same degrees and with the same sign), each repetition's pace (`score.per_rep[].tempo_ratio`, with the `rep` it belongs to) and, on each near miss, `margin_deg`: its size minus its threshold, in degrees. Join `faults[].reps`, `rep_sizes[].rep` and `per_rep[].rep` on the repetition number.

**Side.** The performer's own left and right, never the image's, whatever the camera angle. `left_elbow`, `joints` and `lateral` follow the same rule. Part 3 gives the body in the subject's frame and Part 5 does not mirror a clip; only a feet side file marked `mirrored` has its left and right swapped. `both` is a measure in one direction on the two sides, merged and sized as the mean of the two; `center` is a measure with no side.

**Score v1 to v3.** No measure is renamed or rescaled. The score versions change how a take is charged and capped, not what is detected: a measure name, side, direction and `magnitude_deg` mean the same in a `simon.score.v1` take as in a `simon.score.v3` one (ADR-0018 and ADR-0019 keep detection byte identical). What changes is `score.value` and the fields beside it. v2 weights each miss by how much the trainer moves that measure and caps a take that reports a fault at 89. v3 keeps both and caps a take that reports two or more faults at 79; `score.fault_cap` says which ceiling applied. Values from different score versions are on different scales, so compare `score.value` only within one `score.version` and one `profile`, and read the version from `score.version`, not from `schema_version`. One change to the score itself had no version either: on 2026-10-30 ADR-0013 made the `score.value` of a `simon.score.v1` take the mean of its windows (05312b7), so a v1 value from before it is not on the same scale as one after it for a take longer than one window, and `score.basis` and `score.timeline` appear in `1.2.0`, `1.3.0` or `1.4.0` documents (by content, ADR-0013 left the version alone) written between 05312b7 and the `1.5.0` change d3250dc (the file lists it under `score_changes_without_a_version`). Three changes outside the score altered what a document holds without a version, and the file lists them: attempt 4 redefined `trunk_lean_side` for a deep forward hinge (2026-10-31), attempt 5 stopped reading a foot measure that jitters (2026-11-01), and every tempo became null on a low match (TICKET-063, 2026-11-01).

**An absent measure.** Absent does not mean fine on its own. A measure that is not in `faults[]` was compared and found within its threshold (or too brief to count) only when `status.code` is `ok` (a refusal from before `1.4.0` has `faults` `[]` and no `warnings`, and nothing was compared), the take has no `warnings`, the measure is not in `diagnostics.visibility.excluded` and, for the two foot measures, it is in `diagnostics.feet.compared`. Otherwise it was not measured. The document does not list the measures it compared. `diagnostics.near_misses` lists the candidates that came past a threshold and were dropped, because they were too brief or a kept fault explained them; it is not a list of faults and never changes the score. A null tempo is the same kind of answer: `ratio` null means not measured (a low match, or an example stretch under one second), never on time, and so is a null `score.per_rep[].tempo_ratio`. On time is a ratio from 0.85 to 1.15 with a null `cue`.

**Score credit (1.13.0).** `score.credit` (`simon.credit.v1`, ADR-0020) is listed with `score.credit.percent`, `.points`, `.max_points`, `.levels`, `.grades` and `.per_window[]`. It is reported only: it sets no grade of the score, no cap and no gate, `score.value` and `score.grade` never read it, and the warning cap of 59 does not apply to it, so read `warnings` first. `score.credit.grade` is informational: it is the credit percent's own letter on the credit's own scale, `score.credit.grades` (the team's game scale: S 95, A 85, B 75, C 65, D 55, E 45, F 30, and under 30 still F; S and E are credit letters only), never `score.grade`, whose bands stay A to F, and it ignores warnings and caps, so a take capped to F can show a credit grade of B. Only the 22 body measures of `part5.measures.MEASURES` earn credit; the foot measures (`foot_rotation`, `ankle_inversion`, from the optional foot files) are compared and can be reported as faults, but earn none. It is null when nothing was compared. Compare `score.credit.percent` across takes within one profile; `points` are counted on the example's clock, so they grow with the example's length and the measures seen and not with how long the follower took: compare them only with `max_points` of the same take, or between takes of one example.

### The feet side input (optional, ADR-0015)

Part 3 does not carry Part 2's heel and toe points (its `simon.animation.v1` has the 17 joints, and Part 2's CONTRACT.md "Extra joints (optional)" says Part 3 leaves `extra_joints` alone), so Part 5 reads them from Part 2's own `pose3d.json`, one file per clip, as a side input: `--expected-feet PATH`, `--follower-feet PATH`, with `--expected-feet-person N` and `--follower-feet-person N` (default 0, matched to `people[].id`). `part5.pipeline.run(..., expected_feet=, follower_feet=, expected_feet_person=, follower_feet_person=)` takes the same four.

- **Shape.** Part 2's: `{"frames": [{"frame": int, "t_ms": float, "people": [{"id": int, "joints": {<17 COCO names>: {x, y, z, conf}}, "extra_joints": {left_big_toe, left_small_toe, left_heel, right_big_toe, right_small_toe, right_heel: {x, y, z, conf}}}]}], "t0_pts_ms": float, "mirrored": bool (optional), "provenance": {...}}`. A synthetic file uses the same shape (`provenance.source` `synthetic`). Only the two hips and the six foot points are read; unknown names, the knees and ankles included, are ignored.
- **Measures.** `foot_rotation` and `ankle_inversion`, left and right, per side-file frame, inside the side file's own frame from its own joints and `extra_joints`. A point is seen when it is present, finite and `conf` is at least 0.5. If the top-level `mirrored` is true the left and right series are swapped.
- **Time.** A clip frame at time `t` (the clip's own `t`, seconds) takes the side frame whose `(t_ms - t0_pts_ms) / 1000` is nearest, within half the file's median frame step over all its frames (at least 0.008 s); otherwise that frame's foot values are NaN. `t0_pts_ms` defaults to 0.
- **Errors (exit 1, `part5 analyse: <file>: ...`).** The file is unreadable or not this shape (a `people` entry that is not an object is not this shape); the person id is in no frame (the message lists the ids present); no clip frame matches a frame of the file in time. **Not errors:** a file with no `extra_joints` (Part 2's cpu backend) or a pair where only one clip has feet: the foot measures are hidden for the pair and `diagnostics.feet.hidden_reason` says why. A foot measure is used when it is a number in at least 80% of the clip's frames and steady (its frame-to-frame jitter is at most the `max_jitter_deg` of its entry in `rules.json`, 4 degrees a frame: the far foot of a side view jitters and is left out), and only when usable on both sides. A take compared repetition by repetition compares them rep by rep (ADR-0017).
- **Check.** `python -m part5 doctor pose3d.json` accepts a Part 2 `pose3d.json` as a feet side input (a note says whether it has foot points) and still says it is not a clip.

They are the `pinned` entries of `contracts/sources.json`: `make contracts-check` reports a note, never a failure, if Part 4's files change after the pin.

## Fault labels

Part 3's kit names its faults differently from Part 5's labels. Mapping from Part 3's `CONTRACT.md` ("Conformance kit and Part 5 fault names"):

| Part 3 kit `type` | Closest Part 5 `type` | Part 3 measure | Part 5 measure |
|---|---|---|---|
| `feet_wide` | `foot_out` | `ankle_lateral_offset`, metres, one label for both feet | `thigh_direction`, degrees, one label per side |
| `elbows_out` | `arms_wider` | `upper_arm_abduction`, degrees, both shoulders | `upper_arm_direction`, degrees, per side or `both` |
| `shallow_squat` | `knees_shallow` | `knee_angle_at_bottom`, interior angle, grows as the knee straightens | `knee_flexion`, bend (180 minus interior), shrinks |
| `knee_caving` | `knee_caving` | `thigh_inward_turn_at_bottom`, degrees, one knee | `knee_valgus`, degrees, the knee's offset inside the hip to ankle line, one label per side |
| `correct` | a take with `correct: true` and no faults | none | none |

Only `elbows_out` and `arms_wider` measure the same thing. A size in metres for `feet_wide` is not a size for `foot_out`. Part 3's `knee_caving` maps to Part 5's `knee_valgus` measure (a knee caving in), but the two sizes are different angles: the kit's is a thigh turn at the bottom of the squat, Part 5's is the knee's offset from the hip to ankle line. Part 3's kit has no `elbow_bent` or `trunk_lean`.

Part 5's own foot types (ADR-0015, `labels.json` only; Part 3's kit has none): `foot_turned_out` is `foot_rotation` `more`, `foot_turned_in` is `foot_rotation` `less`, `ankle_rolled_in` is `ankle_inversion` `more` and `ankle_rolled_out` is `ankle_inversion` `less`, each on `left`, `right` or `both`. A take may carry `expected_feet` and `follower_feet`, paths from the repository root to the pose3d.json files its feet come from, like `expected` and `follower`.
